1. `main`에서 브랜치를 만든다. 담당자마다 하나씩: `docs/req-blog-post-social`, `docs/req-game-shop-town`
2. 맡은 영역의 요구사항을 [4.0 작성 양식](#40-작성-양식)에 맞춰 상세화한다.
3. PR을 올리고, 다른 팀원 1명 이상이 읽고 승인(Approve)하면 merge한다.
4. 요구사항 ID는 **한 번 정하면 바꾸지 않는다.** 없앤 요구사항은 지우지 말고 상태를 `❌ 제외`로 바꾼다. (다른 문서와 코드가 ID로 서로를 가리키기 때문)
5. 고치면 위 변경 이력에 한 줄 추가한다.

## 1. 개요

### 1.1 배경

Tistory 같은 블로그는 글쓰기 도구로는 훌륭하지만, 꾸준히 쓰게 만드는 동기가 약하다.
Blogville은 **블로그 활동을 게임 보상과 연결**해서, 글을 쓸수록 캐릭터와 블로그 공간이 성장하는 경험을 준다.

### 1.2 목표

1. **글쓰기와 꾸미기가 우선**인 블로그를 만든다. 게임 요소는 글쓰기를 돕는 역할에 머문다.
2. 소셜 로그인으로 가입 장벽을 낮춘다.
3. 중앙 광장에서 다른 사람의 블로그를 자연스럽게 발견하게 한다.
4. 2D로 완성한 뒤 2.5D(아이소메트릭)로 확장한다.

### 1.3 범위 밖 (이번 프로젝트에서 하지 않는 것)

- 실시간 멀티플레이 (광장에서 다른 사람이 움직이는 모습을 실시간으로 보기)
- 유료 결제 (코인은 활동으로만 얻는다)
- 모바일 앱 (반응형 웹으로 대응)

## 2. 사용자

| 사용자 | 설명 |
|---|---|
| 방문자 | 로그인하지 않은 사람. 공개 글과 블로그, 광장을 구경할 수 있다 |
| 회원 | 사이트 아이디 또는 소셜 계정으로 가입하고 온보딩을 마친 사람. 자기 블로그를 운영하고 다른 블로그와 교류한다 |
| 관리자 | 통계와 회원 목록을 보고, 문제가 있는 글을 삭제한다. 아이템 데이터는 초기에 시드 스크립트로 관리한다 |

## 3. 핵심 사용자 흐름

```text
[처음 방문] → 회원가입·로그인 (사이트 아이디, 또는 네이버 / 카카오 / 구글)
     │
     ▼ 최초 가입이면
[온보딩] 닉네임 → 블로그 이름·주소 → 기본 캐릭터 고르기 (남자·여자 주민 중 1)
     │
     ▼
[중앙 광장] 내 캐릭터로 돌아다님 (광장이 메인. 다른 장소는 건물 입구로 들어간다)
     ├─ 🏠 내 집  → 내 블로그
     ├─ 🏘 이웃집들 → 다른 사람 블로그 (최근 글 쓴 블로그, 내 이웃)
     ├─ 📋 게시판 ─┬─ 왼쪽: 마을 소식 → 마을 최신 글
     │             └─ 오른쪽: 출석 도장 → 일일 보상(출석)
     ├─ 🏪 상점   → 캐릭터·배경 구매
     └─ 🐮 동물 농장 → (준비 중) 동물을 키워 경험치·레벨업
     
[내 블로그] 상단: 미니룸(배경 + 캐릭터) / 하단: 글 목록
     ├─ ✏️ 글쓰기 → 저장 → 경험치·코인 획득
     └─ 🎨 꾸미기 → 보유한 캐릭터·배경 장착

광장 밖 어느 화면에서든 헤더의 [← 광장으로 나가기]로 광장에 돌아온다.
```

## 4. 기능 요구사항

### 4.0 작성 양식

각 영역은 **① 요약 표**와 **② 상세 명세**로 쓴다. 요약 표로 전체를 훑고, 상세 명세로 "무엇이 되면 완성인가"를 정한다.

#### 표기

| 항목 | 값 |
|---|---|
| 우선순위 (MoSCoW) | **M**ust 없으면 서비스가 성립하지 않음 · **S**hould 있어야 기획 의도가 삶 · **C**ould 여유 있으면 · **W**on't 이번엔 안 함 |
| 상태 | ✅ 구현됨 · 🚧 진행 중 · ⬜ 미구현 · ❌ 제외 |
| 담당 | 상세 명세를 쓰고 구현을 책임지는 사람 (GitHub 아이디) |

#### ① 요약 표

```markdown
| ID | 요구사항 (한 문장) | 우선 | 상태 | 담당 |
|---|---|---|---|---|
| XXX-01 | ~할 수 있다 | M | ⬜ | 아이디 |
```

#### ② 상세 명세 (요구사항 하나마다)

```markdown
##### XXX-01 요구사항 이름

| 항목 | 내용 |
|---|---|
| 우선 / 상태 / 담당 | M / ⬜ / 아이디 |
| 사용자 | 방문자 · 회원 · 관리자 중 누가 하는가 |
| 선행 조건 | 이 기능을 쓰기 전에 만족해야 하는 상태 |
| 관련 | 화면 주소 · 테이블 · 다른 요구사항 ID |

**기본 흐름** (문제가 없을 때)
1. 사용자가 ~한다
2. 시스템이 ~한다

**예외 흐름** (입력이 틀리거나 상황이 다를 때)
- 상황 → 시스템 반응 / 보여줄 문구

**입력 규칙**
- 항목: 길이, 허용 문자, 필수 여부

**표시 규칙** (화면에 무엇을, 몇 개, 어떤 순서로)
- 개수 · 정렬 · 페이지 나누기 · 자르는 길이 · 빈 화면 문구 · 날짜 형식

**구현 방식** (어떻게 동작하는가)

| 항목 | 내용 |
|---|---|
| 화면 | 서버 컴포넌트 / 클라이언트 컴포넌트, 파일 경로 |
| 처리 | Server Action 이름과 파일, 처리 순서 |
| 데이터 | 읽고 쓰는 테이블, 핵심 쿼리 |
| 무결성 | 트랜잭션, 잠금, DB 제약조건 |
| 검증 | 어디서 무엇을 검사하는가 (브라우저 / 서버 / DB) |
| 갱신 | 처리 뒤 화면을 어떻게 다시 그리는가, 어디로 이동하는가 |

**수용 기준** (모두 만족하면 완성. 테스트 시나리오로 그대로 쓴다)
- [ ] ~하면 ~된다

**열린 질문** (팀에서 정해야 할 것)
- ~는 어떻게 할까?
```

#### 쓸 때 기억할 것

- **한 요구사항에는 한 가지 기능만.** "가입·로그인"처럼 두 개가 붙어 있으면 나눈다.
- **수용 기준은 확인할 수 있게.** "빠르게 열린다" 대신 "1초 안에 열린다", "잘 보인다" 대신 "모바일(375px)에서 가로 스크롤이 없다".
- **보여줄 문구는 그대로 적는다.** 오류 문구가 정해져 있어야 화면 담당과 서버 담당이 같은 말을 쓴다.
- **모르는 건 지어내지 말고 열린 질문에 적는다.** 회의에서 정하고 나면 본문으로 옮긴다.
- **이미 구현된 기능은 코드의 실제 값을 적는다.** (한 페이지 개수, 글자 수 제한, 정렬 등) 값을 바꾸고 싶으면 열린 질문에 "현재 8개 → 10개로?"처럼 적는다.
- **구현 방식은 처음 보는 팀원이 코드를 찾아갈 수 있을 만큼** 쓴다. 파일 경로와 함수 이름을 적는다.

#### 상세 명세

##### AUTH-07 아이디 회원가입

| 항목 | 내용 |
|---|---|
| 우선 / 상태 / 담당 | M / ✅ / ehgo508 |
| 사용자 | 방문자 |
| 선행 조건 | 로그인하지 않은 상태 |
| 관련 | 화면 `/`, `/onboarding` · 테이블 `users`, `accounts` · 다음 단계 AUTH-02 |

**기본 흐름**
1. 첫 화면에서 [회원가입] 탭을 누른다.
2. 아이디, 비밀번호, 비밀번호 확인을 입력하고 [회원가입]을 누른다.
3. 시스템이 계정을 만들고 **바로 로그인 상태**로 만든다.
4. 온보딩 화면(`/onboarding`)으로 이동한다.

**예외 흐름**
| 상황 | 보여줄 문구 |
|---|---|
| 아이디 형식이 틀림 | 아이디는 영문 소문자, 숫자, _ 로 4~20자예요 |
| 비밀번호가 8자 미만 | 비밀번호는 8자 이상이에요 |
| 비밀번호와 확인이 다름 | 비밀번호가 서로 달라요 |
| 이미 있는 아이디 | 이미 있는 아이디예요 |

오류가 나도 입력한 아이디는 지워지지 않고 남는다.

**입력 규칙**
- 아이디: 영문 소문자·숫자·`_`, 4~20자. 대문자로 입력하면 소문자로 바꿔 저장한다.
- 비밀번호: 8~64자. 문자 종류 제한 없음.

**표시 규칙**
- 첫 화면 오른쪽 카드에 [로그인] [회원가입] 탭. 처음에는 [로그인] 탭이 열려 있다.
- 회원가입 칸: 아이디(아래 안내 `영문 소문자, 숫자, _ 로 4~20자`) · 비밀번호(`비밀번호 (8자 이상)`) · 비밀번호 확인 · [회원가입]
- 오류는 버튼 바로 위에 빨간 굵은 글씨 한 줄
- 처리 중에는 버튼이 `가입하는 중...`으로 바뀌고 눌리지 않는다.

**구현 방식**

| 항목 | 내용 |
|---|---|
| 화면 | `src/app/page.tsx`(서버, 이미 로그인했으면 광장/온보딩으로 보냄) + `LoginButtons`·`SignUpForm` (클라이언트, `src/components/login-buttons.tsx`, `useActionState`) |
| 처리 | `signUp` (`src/app/(auth)/actions.ts`): zod 검증 → Better Auth `auth.api.signUpEmail` (username 플러그인). 아이디로만 가입하므로 이메일 자리에 `아이디@users.blogville.invalid`를 넣는다 (라이브러리가 이메일을 필수로 요구) |
| 데이터 | `users`(username, display_username, role 기본 `user`) + `accounts`(provider_id `credential`, password = 해시) + `sessions`(가입과 동시에 로그인) |
| 검증 | 브라우저 `required`·`minLength`·`maxLength` / 서버 zod / Better Auth username 검사(4~20자, `[a-z0-9_]`) / DB UNIQUE(`users.username`, `users.email`) |
| 보안 | `role`은 `input: false`라서 가입 요청으로 바꿀 수 없다. 비밀번호는 Better Auth `hashPassword`로 해시 |
| 갱신 | 로그인 쿠키 설정(`nextCookies` 플러그인) → `revalidatePath("/", "layout")` → `/onboarding`으로 이동 |

**수용 기준**
- [x] 가입하면 별도 로그인 없이 온보딩 화면으로 이동한다.
- [x] `Tester1`로 가입하면 아이디는 `tester1`로 저장되고, 이후 `tester1`이나 `TESTER1`로 다시 가입할 수 없다.
- [x] 비밀번호는 원문이 아니라 해시로만 저장된다 (`accounts.password`).

## 5. 비기능 요구사항

> 담당 **ehgo508**
