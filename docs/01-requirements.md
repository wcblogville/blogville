## 1. 개요

### 1.1 배경

Tistory 같은 블로그는 글쓰기 도구로는 훌륭하지만, 꾸준히 쓰게 만드는 동기가 약하다.
Blogville은 **블로그 활동을 게임 보상과 연결**해서, 글을 쓸수록 캐릭터와 블로그 공간이 성장하는 경험을 준다.

### 1.2 목표

1. **글쓰기와 꾸미기가 우선**인 블로그를 만든다. 게임 요소는 글쓰기를 돕는 역할에 머문다.
2. 소셜 로그인으로 가입 장벽을 낮춘다.
3. 중앙 광장에서 다른 사람의 블로그를 자연스럽게 발견하게 한다.
4. 2D로 완성한 뒤 2.5D(아이소메트릭)로 확장한다.

### 1.3 범위 밖 (이번 프로젝트에서 하지 않는 것)

- 실시간 멀티플레이 (광장에서 다른 사람이 움직이는 모습을 실시간으로 보기)
- 유료 결제 (코인은 활동으로만 얻는다)
- 모바일 앱 (반응형 웹으로 대응)

## 2. 사용자

| 사용자 | 설명 |
|---|---|
| 방문자 | 로그인하지 않은 사람. 공개 글과 블로그, 광장을 구경할 수 있다 |
| 회원 | 사이트 아이디 또는 소셜 계정으로 가입하고 온보딩을 마친 사람. 자기 블로그를 운영하고 다른 블로그와 교류한다 |
| 관리자 | 통계와 회원 목록을 보고, 문제가 있는 글을 삭제한다. 아이템 데이터는 초기에 시드 스크립트로 관리한다 |

## 3. 핵심 사용자 흐름

```text
[처음 방문] → 회원가입·로그인 (사이트 아이디, 또는 네이버 / 카카오 / 구글)
     │
     ▼ 최초 가입이면
[온보딩] 닉네임 → 블로그 이름·주소 → 기본 캐릭터 고르기 (3종 중 1)
     │
     ▼
[중앙 광장] 내 캐릭터로 돌아다님
     ├─ 🏠 내 집  → 내 블로그
     ├─ 🏘 이웃집들 → 다른 사람 블로그 (최근 글 쓴 블로그, 내 이웃)
     ├─ 📮 우체통 → 일일 보상(출석)
     ├─ 🏪 상점   → 캐릭터·배경 구매
     └─ 📋 게시판 → 마을 최신 글
     
[내 블로그] 상단: 미니룸(배경 + 캐릭터) / 하단: 글 목록
     ├─ ✏️ 글쓰기 → 저장 → 경험치·코인 획득
     └─ 🎨 꾸미기 → 보유한 캐릭터·배경 장착
```

## 4. 기능 요구사항

### 4.0 작성 양식

각 영역은 **① 요약 표**와 **② 상세 명세**로 쓴다. 요약 표로 전체를 훑고, 상세 명세로 "무엇이 되면 완성인가"를 정한다.

#### 표기

| 항목 | 값 |
|---|---|
| 우선순위 (MoSCoW) | **M**ust 없으면 서비스가 성립하지 않음 · **S**hould 있어야 기획 의도가 삶 · **C**ould 여유 있으면 · **W**on't 이번엔 안 함 |
| 상태 | ✅ 구현됨 · 🚧 진행 중 · ⬜ 미구현 · ❌ 제외 |
| 담당 | 상세 명세를 쓰고 구현을 책임지는 사람 (GitHub 아이디) |

#### ① 요약 표

```markdown
| ID | 요구사항 (한 문장) | 우선 | 상태 | 담당 |
|---|---|---|---|---|
| XXX-01 | ~할 수 있다 | M | ⬜ | 아이디 |
```

#### ② 상세 명세 (요구사항 하나마다)

```markdown
##### XXX-01 요구사항 이름

| 항목 | 내용 |
|---|---|
| 우선 / 상태 / 담당 | M / ⬜ / 아이디 |
| 사용자 | 방문자 · 회원 · 관리자 중 누가 하는가 |
| 선행 조건 | 이 기능을 쓰기 전에 만족해야 하는 상태 |
| 관련 | 화면 주소 · 테이블 · 다른 요구사항 ID |

**기본 흐름** (문제가 없을 때)
1. 사용자가 ~한다
2. 시스템이 ~한다

**예외 흐름** (입력이 틀리거나 상황이 다를 때)
- 상황 → 시스템 반응 / 보여줄 문구

**입력 규칙**
- 항목: 길이, 허용 문자, 필수 여부

**수용 기준** (모두 만족하면 완성. 테스트 시나리오로 그대로 쓴다)
- [ ] ~하면 ~된다

**열린 질문** (팀에서 정해야 할 것)
- ~는 어떻게 할까?
```

#### 쓸 때 기억할 것

- **한 요구사항에는 한 가지 기능만.** "가입·로그인"처럼 두 개가 붙어 있으면 나눈다.
- **수용 기준은 확인할 수 있게.** "빠르게 열린다" 대신 "1초 안에 열린다", "잘 보인다" 대신 "모바일(375px)에서 가로 스크롤이 없다".
- **보여줄 문구는 그대로 적는다.** 오류 문구가 정해져 있어야 화면 담당과 서버 담당이 같은 말을 쓴다.
- **모르는 건 지어내지 말고 열린 질문에 적는다.** 회의에서 정하고 나면 본문으로 옮긴다.

### 4.1 회원 / 인증 (AUTH)

| AUTH-02 | 처음 로그인하면 온보딩(닉네임, 블로그 이름·주소, 기본 캐릭터)을 거친다. 마치기 전에는 회원 기능을 쓸 수 없다 | M | ✅ | ehgo508 |
| AUTH-03 | 닉네임과 블로그 주소는 서비스 전체에서 중복될 수 없다 | M | ✅ | ehgo508 |
| AUTH-04 | 로그아웃할 수 있다 | M | ✅ | ehgo508 |
| AUTH-05 | 같은 사람이 여러 로그인 수단(아이디, 소셜)을 한 회원에 연결할 수 있다 | C | ⬜ | 미정 |
| AUTH-06 | 회원 탈퇴 시 개인정보와 글을 삭제한다 | S | ⬜ | 미정 |
| AUTH-07 | 사이트 자체 아이디와 비밀번호로 **회원가입**할 수 있다 | M | ✅ | ehgo508 |
| AUTH-08 | 관리자는 관리자 페이지에서 통계·회원 목록을 보고 어떤 글이든 삭제할 수 있다 | S | ✅ | ehgo508 |
| AUTH-09 | 사이트 아이디와 비밀번호로 **로그인**할 수 있다 (AUTH-07에서 분리) | M | ✅ | ehgo508 |

> 아래 상세 명세는 **작성 예시**다. AUTH-07, AUTH-09, AUTH-02는 지금 구현된 동작을 기준으로 썼고, 나머지는 열린 질문을 중심으로 남겼다.

#### 상세 명세

##### AUTH-07 아이디 회원가입

| 항목 | 내용 |
|---|---|
| 우선 / 상태 / 담당 | M / ✅ / ehgo508 |
| 사용자 | 방문자 |
| 선행 조건 | 로그인하지 않은 상태 |
| 관련 | 화면 `/`, `/onboarding` · 테이블 `users`, `accounts` · 다음 단계 AUTH-02 |

**기본 흐름**
1. 첫 화면에서 [회원가입] 탭을 누른다.
2. 아이디, 비밀번호, 비밀번호 확인을 입력하고 [회원가입]을 누른다.
3. 시스템이 계정을 만들고 **바로 로그인 상태**로 만든다.
4. 온보딩 화면(`/onboarding`)으로 이동한다.

**예외 흐름**
| 상황 | 보여줄 문구 |
|---|---|
| 아이디 형식이 틀림 | 아이디는 영문 소문자, 숫자, _ 로 4~20자예요 |
| 비밀번호가 8자 미만 | 비밀번호는 8자 이상이에요 |
| 비밀번호와 확인이 다름 | 비밀번호가 서로 달라요 |
| 이미 있는 아이디 | 이미 있는 아이디예요 |

오류가 나도 입력한 아이디는 지워지지 않고 남는다.

**입력 규칙**
- 아이디: 영문 소문자·숫자·`_`, 4~20자. 대문자로 입력하면 소문자로 바꿔 저장한다.
- 비밀번호: 8~64자. 문자 종류 제한 없음.

**수용 기준**
- [x] 가입하면 별도 로그인 없이 온보딩 화면으로 이동한다.
- [x] `Tester1`로 가입하면 아이디는 `tester1`로 저장되고, 이후 `tester1`이나 `TESTER1`로 다시 가입할 수 없다.
- [x] 비밀번호는 원문이 아니라 해시로만 저장된다 (`accounts.password`).
- [x] 가입 요청으로 관리자 권한(`role`)을 정할 수 없다.

**열린 질문**
- 비밀번호를 잊으면? 이메일을 받지 않아서 지금은 **비밀번호 찾기가 없다.** 이메일을 선택 입력으로 받을까, 관리자가 초기화해 줄까?
- `admin`, `notice` 같은 아이디를 일반 회원이 못 쓰게 막을까? (지금은 먼저 가입한 사람이 가져간다)
- 비밀번호에 영문+숫자 섞기 같은 규칙을 더할까?

##### AUTH-09 아이디 로그인

| 항목 | 내용 |
|---|---|
| 우선 / 상태 / 담당 | M / ✅ / ehgo508 |
| 사용자 | AUTH-07로 가입한 회원, 관리자 |
| 선행 조건 | 로그인하지 않은 상태 |
| 관련 | 화면 `/` · 테이블 `users`, `accounts`, `sessions` |

**기본 흐름**
1. 첫 화면 [로그인] 탭에서 아이디와 비밀번호를 입력하고 [로그인]을 누른다.
2. 시스템이 로그인 세션을 만든다.
3. 광장(`/town`)으로 이동한다. 온보딩을 마치지 않았다면 온보딩으로 이동한다.

**예외 흐름**
| 상황 | 보여줄 문구 |
|---|---|
| 아이디나 비밀번호가 비어 있음 | 아이디와 비밀번호를 적어 주세요 |
| 없는 아이디, 또는 비밀번호가 틀림 | 아이디 또는 비밀번호가 맞지 않아요 |

없는 아이디와 틀린 비밀번호에 **같은 문구**를 보여준다. 어떤 아이디가 가입되어 있는지 알려주지 않기 위해서다.

**수용 기준**
- [x] 맞는 아이디·비밀번호면 광장으로 이동하고 헤더에 레벨·코인·캐릭터가 보인다.
- [x] 아이디는 대소문자를 구분하지 않는다 (`TESTER1`로도 로그인된다).
- [x] 관리자로 로그인하면 헤더에 [👑 관리자] 버튼이 보인다.
- [ ] 같은 아이디로 짧은 시간에 여러 번 틀리면 잠시 로그인을 막는다. → **보완 필요**: 로그인 라이브러리의 시도 횟수 제한은 HTTP 요청에만 적용되는데, 지금 로그인은 서버 코드(Server Action)에서 라이브러리를 직접 부르기 때문에 적용되지 않을 수 있다.

**열린 질문**
- 몇 번 틀리면 몇 분 막을까? (예: 5번 틀리면 5분)
- "로그인 상태 유지" 체크박스가 필요할까? 지금은 세션 기본값(7일)으로 유지된다.

##### AUTH-02 온보딩

| 항목 | 내용 |
|---|---|
| 우선 / 상태 / 담당 | M / ✅ / ehgo508 |
| 사용자 | 로그인했지만 아직 프로필이 없는 회원 |
| 선행 조건 | AUTH-07, AUTH-09 또는 AUTH-01로 로그인 |
| 관련 | 화면 `/onboarding` · 테이블 `profiles`, `blogs`, `user_items`, `categories`, `point_ledger` · AUTH-03, GAME-01 |

**기본 흐름**
1. 닉네임, 블로그 이름, 블로그 주소를 입력하고 기본 캐릭터 3종(모험가·고양이·강아지) 중 하나를 고른다.
2. [광장으로 출발!]을 누르면 시스템이 **한 번에(트랜잭션)** 아래를 처리한다.
   - 고른 캐릭터와 기본 배경(초원) 지급
   - 프로필과 블로그 생성, 기본 카테고리 "일상" 생성
   - 가입 축하 🪙 100 코인 지급
3. 광장으로 이동해 환영 메시지를 보여준다.

**예외 흐름**
| 상황 | 보여줄 문구 |
|---|---|
| 닉네임 2자 미만 / 12자 초과 | 닉네임은 2자 이상이에요 / 닉네임은 12자까지예요 |
| 이미 있는 닉네임 | 이미 있는 닉네임이에요 |
| 블로그 주소 형식이 틀림 | 주소는 영문 소문자, 숫자, _ 로 3~20자예요 |
| 이미 있는 주소 | 이미 있는 주소예요 |
| 예약된 주소 (`admin`, `api`, `town`, `feed`, `shop`, `closet`, `write`, `settings`, `blog`, `onboarding`) | 이 주소는 쓸 수 없어요 |

**수용 기준**
- [x] 온보딩 전에 글쓰기·상점 등 회원 화면에 들어가면 온보딩으로 돌아온다.
- [x] 처리 중 하나라도 실패하면 아무것도 저장되지 않는다.
- [x] 온보딩을 마친 뒤 `/onboarding`에 들어가면 광장으로 이동한다.

##### GAME-05 보상 규칙과 하루 상한

| 항목 | 내용 |
|---|---|
| 우선 / 상태 / 담당 | S / ✅ / jiwon934 |
| 사용자 | 회원 |

**기본 흐름**
1. 회원이 보상 받는 활동을 한다. (위 보상 규칙 표)
2. 시스템이 회원 단위 잠금(advisory lock)을 건 트랜잭션에서 **오늘 같은 사유로 받은 횟수**를 원장에서 센다.
3. 하루 상한보다 적으면 원장에 경험치·코인을 기록하고, 상한에 닿았으면 아무것도 기록하지 않는다. 활동 자체(글 저장, 댓글 등록)는 그대로 성공한다.

로그인 라이브러리(Better Auth)에는 "로그인 요청 10초에 3번" 같은 기본 제한이 있지만, **배포 환경에서 HTTP 요청으로 들어올 때만** 적용된다. 우리 로그인 화면은 서버 코드(Server Action)에서 라이브러리를 직접 부르기 때문에 이 제한이 걸리지 않을 수 있다.

- [ ] 성공하면 실패 횟수가 초기화된다.
- [ ] 없는 아이디도 똑같이 막아서, 어떤 아이디가 있는지 알 수 없게 한다.
