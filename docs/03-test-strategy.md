# Blogville 테스트 전략과 품질 관리

> 버전 1.0 (2026-10-15). 무엇을, 언제, 어디서, 어떤 기준으로 검사하는지 정한다.
> 요구사항은 [01-requirements.md](01-requirements.md), 요구사항마다 어느 시험이 확인하는지는 [04-test-trace.md](04-test-trace.md)(자동 생성).

## 1. 목표

1. **회원이 먼저 발견하는 고장이 없게** 한다. 운영(`main`)에 들어가기 전에 자동 검사가 막는다 (NF-23).
2. **요구사항마다 확인하는 시험이 있게** 한다. 구현된 요구사항(✅·🚧)의 시험 연결률을 숫자로 본다.
3. **느려지지 않게** 한다. 주요 화면의 Lighthouse 성능 점수를 매일 재고 기준 아래로 떨어지면 알린다 (NF-07).
4. **시험을 믿을 수 있게** 한다. 가끔 실패하는 시험(flaky)은 "운이 나빴다"로 넘기지 않고 원인을 고친다.

## 2. 테스트 피라미드

아래로 갈수록 빠르고 많이, 위로 갈수록 느리지만 실제 사용과 가깝다.

| 층 | 무엇 | 도구 | 위치 | 개수 | 걸리는 시간 |
|---|---|---|---|---|---|
| 정적 검사 | 타입·코드 규칙 | `tsc --noEmit`, `eslint` | 코드 전체 | - | 30초 |
| 단위 | 순수 함수·규칙 계산 (레벨 공식, 이름 규칙, HTML 정화, 마을 지형·길, 방 길 찾기 등). DB·브라우저 없음 | `tsx` 스크립트 | `scripts/test-*.ts` (`npm test`) | 13개 | 10초 |
| E2E | 실제 브라우저로 화면을 누르고 DB 결과까지 확인 | Playwright + `pg` | `e2e/*.mjs` | 48개 | 1~3분/개 |
| 성능 | 첫 화면·블로그·상점 등의 Lighthouse 점수 | Lighthouse | `scripts/lighthouse.mjs` | 6개 화면 | 2분 |

- **단위 테스트를 먼저** 쓴다. 숫자·규칙(경험치, 확률, 좌표, 이름 검사)은 화면을 띄우지 않고도 확인할 수 있다. 계산을 `src/lib/`의 순수 함수로 빼 두는 이유다.
- **E2E는 회원이 실제로 하는 흐름**만 쓴다: 가입 → 글쓰기 → 상점 → 우리 집 → 광장. 화면 문구·버튼 이름(접근성 이름)으로 찾아서, 디자인이 바뀌어도 덜 깨지게 한다.
- **DB 결과까지 확인**한다. 화면에 "샀어요"가 떠도 원장(`point_ledger`)에 기록이 없으면 실패다.
- E2E는 **실행마다 새 회원**(`이름 + 시각`)을 만들어 서로 영향을 주지 않는다. 그래서 같은 DB에서 몇 번을 돌려도 된다.

## 3. 언제 무엇이 도나 (품질 관문)

| 언제 | 워크플로 | 무엇 | 실패하면 |
|---|---|---|---|
| 내 컴퓨터, 커밋 전 | - | `npx tsc --noEmit && npx eslint && npm test`, 바꾼 영역의 E2E | 고치고 커밋 |
| `develop`·`main`으로 가는 PR | `ci.yml` "검사" | 코드 검사(타입·린트·단위·연결표 최신인지) + 빌드·E2E(**CI 묶음** 11개) | PR을 합칠 수 없다 (ruleset 필수 검사) |
| `main`에 push (배포) | `deploy.yml` "배포" | 위 검사 전체를 다시 돌리고 통과해야만 배포 | 배포하지 않는다. 사이트는 그대로 |
| 매일 밤 (한국 시간 새벽 3시) | `nightly.yml` "매일 밤 전체 검사" | `develop`에서 **전체 E2E**(48개) + **Lighthouse 성능 기준** | Actions에 빨간 표시 + 요약 표. 다음 날 원인을 고친다 |

- **CI 묶음**과 **매일 밤 묶음**은 `e2e/suites.json` 한 곳에서 정한다. 실행은 `node scripts/e2e-run.mjs ci|nightly|<파일 이름...>`.
- PR마다 전체(48개)를 돌리면 30분이 넘어 개발이 느려진다. 그래서 **자주 깨지고 회원이 많이 쓰는 흐름**만 PR에서, 나머지는 매일 밤 돈다.
- CI 묶음에 넣는 기준: ① 돈·아이템이 오가는 곳(상점·성장·원장) ② 로그인·글쓰기 ③ 광장·우리 집처럼 그림·좌표가 복잡해 자주 깨지는 곳.

## 4. 결과 보는 법

- PR 화면 아래 **검사** 두 줄(코드 검사·빌드·E2E)이 초록이면 통과.
- Actions 실행 화면의 **Summary**에 E2E 표(시험마다 ✅/❌·시간·실패 이유), 요구사항 연결률, Lighthouse 점수 표가 붙는다.
- 실패하면 같은 화면 아래 **Artifacts**의 `e2e-failure`(스크린샷·`app.log`)를 내려받아 본다.

## 5. 품질 지표와 기준

| 지표 | 지금 (2026-10-15) | 기준 | 어디서 보나 |
|---|---|---|---|
| 구현된 요구사항 중 시험이 있는 비율 | 83% | 80% 이상 유지, 새 요구사항은 시험과 함께 | `docs/04-test-trace.md` |
| 그중 PR마다 확인하는 비율 | 51% | 줄어들지 않게 | 같은 파일 |
| 단위 테스트 줄 커버리지 (`src/lib`) | `npm run test:coverage`로 잰다 | 떨어지지 않게 | PR 검사 Summary |
| Lighthouse 성능 (휴대폰 기준) | 첫 화면 85, 블로그 96, 마을 소식 92, 상점 96 | 첫 화면·마을 소식 80, 블로그·상점·꾸미기 85 이상 | 매일 밤 Summary |

광장(`/town`)은 게임 화면(Phaser)이라 Lighthouse의 "막힌 시간(TBT)"이 커서 점수 기준에서 뺀다. 대신 E2E(`town.mjs`)가 걷기·계단·입구를 확인한다.

## 6. 가끔 실패하는 시험 (flaky) 다루기

"다시 돌리니 됐다"는 원인이 아니다. 느린 CI에서만 실패하는 시험은 **시험이 시간에 기대고 있다**는 뜻이다.

1. 실패 기록(스크린샷·로그)으로 어느 줄에서 무엇을 기다리다 실패했는지 본다.
2. **정해진 시간만큼 기다리기(`waitForTimeout`) 대신 조건을 기다린다**: 화면 글자, DB 값, 게임이 내보내는 시험 신호(`data-*` 속성).
3. 키 입력처럼 프레임에 기대는 동작은 **결과가 보일 때까지** 누른다 (예: 광장 계단 시험은 발이 움직일 때까지 키를 누른다).
4. 시험을 끄거나 건너뛰지 않는다. 고친 뒤 CPU를 꽉 채운 느린 상태에서도 로컬로 한 번 더 돌려 본다.

지금까지 고친 예: 성장 촉진제 결과 문구를 레벨업 창이 지워 버림 → DB 값으로 기다림 (`booster.mjs`), 느린 프레임에서 계단을 지나침 → 가까우면 조금씩 걷기 (`town.mjs`).

## 7. 새 기능을 만들 때 (체크리스트)

PR 템플릿(`.github/pull_request_template.md`)에도 같은 목록이 있다.

- [ ] 규칙·계산은 `src/lib/` 순수 함수로 빼고 `scripts/test-*.ts`에 단위 테스트를 더했다
- [ ] 회원이 하는 흐름은 `e2e/`에 시험을 더하거나 고쳤다. 맨 위 주석에 **요구사항 ID**를 적었다
- [ ] `npm run test:trace`로 연결표를 다시 만들었다 (안 하면 CI의 코드 검사가 실패한다)
- [ ] 자주 쓰는 흐름이면 `e2e/suites.json`의 `ci`에, 아니면 `nightly`에 넣었다
- [ ] 화면이 바뀌면 스크린샷으로 확인했다

## 8. 시험 데이터

- CI는 작업마다 **빈 PostgreSQL 17**을 새로 띄우고 `db:migrate` → `db:seed`(아이템) → `admin:create`(관리자)를 한다. 비밀 값은 그 자리에서 만든 임시 값이다.
- 공용 DB(학교 서버)에서는 시험을 돌리지 않는다. `db:reset`은 내 컴퓨터의 개발 DB에서만 쓴다.
- E2E는 `.env.local`의 `DATABASE_URL`로 결과를 확인하므로 **앱 서버와 같은 DB**를 봐야 한다.
